# RUASM — российский ассемблерный язык и компилятор

**Версия:** 1.11.5 · **Цель:** x86-64 · **Лицензия:** MIT · **Языки документации:** русский и английский

RUASM — самостоятельный нативный ассемблерный язык и самохостящийся компилятор. Этот репозиторий содержит готовые компиляторы для Linux и Windows x86-64, исходный код обеих платформ, машинно-читаемый контракт возможностей, подробные спецификации для разработчиков и ИИ-агентов, примеры и сценарии воспроизводимой сборки.

> **Статус реализации.** RUASM 1.11.5 — работающий компилятор для ограниченного, явно описанного подмножества x86-64. Это не полная реализация ISA x86-64, не полноценная замена FASM и пока не законченная инструментальная среда для операционной системы. Цели проекта шире текущей реализации; они перечислены ниже отдельно.

[English README](README.en.md) · [Спецификация компилятора для ИИ-агентов](docs/COMPILER-SPEC-AI-RU.md) · [Спецификация языка для ИИ-агентов](docs/LANGUAGE-SPEC-AI-RU.md)

## 1. Зачем создаётся RUASM

Долгосрочная цель — создать российский ассемблерный язык и компилятор для системного программирования, пригодный для разработки загрузчиков, ядер, драйверов, встроенного ПО и компактных нативных программ. Стратегическая цель следующего уровня — использовать этот язык как один из базовых инструментов разработки суверенной российской операционной системы.

RUASM с самого начала проектируется с приоритетом **предсказуемой работы ИИ-агентов**. Это не просто привычный синтаксис ассемблера с новым именем. Проект развивает проверяемые свойства языка и инструментария:

- явная и версионируемая грамматика;
- машинно-читаемый манифест реальных возможностей конкретного бинарника;
- точные матрицы форм инструкций вместо предположений по одному имени мнемоники;
- единая простая модель исходного файла: один statement на физическую строку;
- регистрозависимые ASCII-идентификаторы и каноническое написание;
- детерминированное разрешение `EQU` и контролируемая стабилизация размещения;
- режим проверки без выдачи результата (`--check`);
- структурированные JSON-диагностики с кодами ошибок;
- самохостинг и проверяемая побайтовая воспроизводимость сборки.

**Проверяемая гипотеза:** явные ограничения и машинные контракты должны уменьшить число ошибочных генераций, повторных компиляций и токенов, затрачиваемых ИИ-агентом на исправление кода. Это гипотеза архитектуры, а не уже доказанное сравнительное преимущество. Для её подтверждения проекту нужны опубликованные контрольные задачи и воспроизводимые эксперименты с агентами.

Наличие мнемоники не означает поддержку всех её архитектурных вариантов. Авторитетный список допустимых форм возвращает запускаемый компилятор по команде `--features=json`. Сводная спецификация не заменяет этот манифест.

`NOP`, `RET`, `SYSCALL`; `MOV`; арифметические и логические операции `ADD`, `ADC`, `SBB`, `SUB`, `AND`, `OR`, `XOR`, `CMP`, `TEST`; `LEA`, `XCHG`; `PUSH`, `POP`; `INC`, `DEC`, `NOT`, `NEG`; `SHL`, `SHR`, `SAR`, `ROL`, `ROR`, `RCL`, `RCR`; переходы `JMP`, `CALL` и условные `Jcc`; `SETcc`, `CMOVcc`; `BSWAP`, `MOVZX`, `MOVSX`; `MUL`, `IMUL`, `DIV`, `IDIV`; `BT`, `BTS`, `BTR`, `BTC`.

Подробные ограничения ширин и операндов описаны в [спецификации языка](docs/LANGUAGE-SPEC-AI-RU.md) и в [`ruasm-features-v29.example.json`](spec/contracts/ruasm-features-v29.example.json).

## 3. Быстрый старт

### Linux x86-64

```sh
chmod +x ./bin/linux-x86_64/ruasm

# Узнать версию и фактические возможности компилятора.
./bin/linux-x86_64/ruasm --version=json
./bin/linux-x86_64/ruasm --features=json > features.json

# Проверить пример, не создавая бинарный файл.
./bin/linux-x86_64/ruasm examples/hello.asm --check

# Скомпилировать пример в плоский бинарный образ.
mkdir -p build
./bin/linux-x86_64/ruasm examples/hello.asm -o build/hello.bin

# Получить JSON-диагностику при ошибке.
./bin/linux-x86_64/ruasm examples/hello.asm --check --diagnostics=json
```

### Windows x86-64 (PowerShell 7)

```powershell
$ruasm = '.\bin\windows-x86_64\ruasm.exe'

& $ruasm --version=json
& $ruasm --features=json | Set-Content -Encoding utf8 .\features.json
& $ruasm .\examples\hello.asm --check

New-Item -ItemType Directory -Force .\build | Out-Null
& $ruasm .\examples\hello.asm -o .\build\hello.bin
if ($LASTEXITCODE -ne 0) { throw 'RUASM compilation failed' }
```

### Первый исходник

```asm
; examples/hello.asm
entry:
    mov eax, 42
    ret
```

Этот пример создаёт две инструкции x86-64. Компилятор выдаёт **сырые байты**, а не самостоятельный исполняемый файл ОС. Для запуска результата вызывающая среда должна загрузить его в память и обеспечить выбранный ABI, стек и прочие предусловия.

Ещё примеры находятся в каталоге [`examples/`](examples/).

## 4. Обязательный рабочий протокол ИИ-агента

Перед генерацией кода агент должен обращаться к тому бинарнику, который фактически будет использоваться:

1. Выполнить `ruasm --version=json` и проверить версию, хост и цель.
2. Выполнить `ruasm --features=json`; проверить `schema_version` и сохранить манифест.
3. Для каждой инструкции проверить **точную** форму операндов, порядок, ширину и ограничения immediate/memory.
4. Не выводить поддержку формы из названия инструкции, внешней документации или опыта работы с другим ассемблером.
5. Генерировать ASCII, lowercase-синтаксис и один statement на строку.
6. Выполнить `input.asm --check --diagnostics=json`.
7. Исправлять только ошибки, названные диагностикой; не перебирать неподтверждённые формы наугад.
8. Компилировать в новый путь и проверять код возврата, размер и ожидаемые байты/хеш.

Подробный контракт: [COMPILER-SPEC-AI-RU.md](docs/COMPILER-SPEC-AI-RU.md). Грамматика и семантика: [LANGUAGE-SPEC-AI-RU.md](docs/LANGUAGE-SPEC-AI-RU.md). Для англоязычных агентов доступны соответствующие документы `*-EN.md`.

## 6. Пересборка и проверка воспроизводимости

Linux-компилятор может пересобрать оба целевых бинарника:

```sh
./scripts/rebuild-linux.sh
./scripts/rebuild-windows-cross.sh
```

Обе команды сравнивают результат с опубликованным бинарником через `cmp`. Побайтовое совпадение подтверждает воспроизводимость соответствующей сборки в текущем окружении.

Для пересборки Windows из Windows используйте PowerShell:

```powershell
.\scripts\rebuild-windows.ps1
```

Общая платформа и core могут быть изменены, после чего полные translation units пересоздаются командой:

```sh
./tools/compose-sources.sh
```

После изменений выполните `./scripts/verify-package.sh`, пересоберите обе платформы и обновите `SHA256SUMS`.

## 7. Архитектурные границы и известные отсутствующие возможности

В версии 1.11.5 отсутствуют: полный охват x86-64 ISA, макропроцессор и препроцессор, `include`, строковые литералы, `org`, `align`, секции, `times`, резервирование/включение файлов, RIP-relative адресация, сегментные переопределения, объектные ELF/COFF-файлы, релокации, линкер, экспорт символов, ABI-декларации, генерация стековых кадров, отладчик, SDK и стандартная библиотека целевой ОС. См. полный перечень в спецификации языка.

Компилятор не обещает, что произвольный плоский образ можно запустить непосредственно как процесс Linux или Windows. Он не предоставляет загрузчик и не выбирает ABI за пользователя.

## 8. Дорожная цель

Проект развивается к следующей системе целей:

1. Достичь полного и точно специфицированного покрытия нужного подмножества/набора ISA для системного программирования, постепенно расширяя его до конкурентного по функциональности уровня.
2. Измерять скорость компиляции и размер результата на общих воспроизводимых наборах задач; улучшать их без нарушения корректности.
3. Снижать размер самого компилятора и генерируемого кода, измеряя каждый результат, а не полагаясь на впечатления.
4. Сделать язык удобным для генерации ИИ-агентами за счёт формальной грамматики, семантики, ограниченных форм, стабильной диагностики и машиночитаемого контракта.
5. Проверять гипотезу снижения токенов/ошибок агентов на опубликованных сравнительных тестах.
6. Создать воспроизводимую и документированную цепочку независимой эволюции собственного компилятора, не заимствуя реализацию сторонних компиляторов.
7. В перспективе использовать RUASM для создания загрузочной и системной инфраструктуры российской операционной системы.

Это цели разработки, а не заявление о достигнутом паритете с FASM, превосходстве по скорости или завершённой готовности к ОС.

## 10. Обратная связь и вклад

Изменения языка должны сопровождаться изменением спецификации, схемы/примера `--features=json` и тестов. Изменения машинного интерфейса должны иметь новую версию схемы, если они несовместимы. Не документируйте новую возможность до тех пор, пока она не реализована и не проверяется.

Перед предложением изменения агенту или разработчику следует указать: затрагиваемый контракт, минимальный тест, ожидаемые байты, влияние на совместимость и результаты воспроизводимой сборки.
