# Спецификация компилятора RUASM для ИИ-агентов

**Версия документа:** 1.0  
**Базовая версия компилятора:** RUASM 1.11.5  
**Контракт возможностей:** схема 29  
**Целевая архитектура:** x86-64  
**Формат результата:** плоский бинарный образ, не более 65 536 байт  
**Нормативное машинно-читаемое приложение:** [`spec/contracts/ruasm-features-v29.example.json`](../spec/contracts/ruasm-features-v29.example.json)

## 1. Назначение и правила соответствия

Документ задаёт наблюдаемый контракт командной строки, компиляции, выходных данных, диагностики и машинно-читаемого интерфейса RUASM 1.11.5. Он предназначен как для разработчиков, так и для автономных ИИ-агентов.

RUASM — самохостящийся нативный ассемблерный язык и компилятор для ограниченного набора x86-64. Долгосрочная область применения: системное ПО, загрузчики, ядра, драйверы, встроенное ПО и компактные нативные компоненты. Текущая версия реализует подмножество возможностей; это пока не полный ассемблер x86-64 и не законченная инструментальная среда операционной системы.

**Правило соответствия:** наличие мнемоники в списке не означает поддержку всех её архитектурных форм. Агент ОБЯЗАН получить точные формы из `--features=json` именно того исполняемого файла, который будет использоваться. Запрещено выводить поддержку из документации Intel/AMD, другого ассемблера или знания названия инструкции.

Приоритет источников:

1. `--version=json` и `--features=json` запущенного бинарного файла — истина для данного бинарного файла.
2. Версионируемые JSON Schema в `spec/contracts/` задают структуру машинного интерфейса.
3. Настоящий документ объясняет контракт версии 1.11.5.
4. Примеры иллюстрируют стиль; они не расширяют грамматику.

Если бинарный файл сообщает другую версию схемы возможностей, агент ОБЯЗАН прекратить использование предположений схемы 29 и изучить новый контракт.

## 2. Артефакты дистрибутива

| Артефакт | Путь | Формат | Размер в этом комплекте |
|---|---|---|---:|
| Компилятор Linux | `bin/linux-x86_64/ruasm` | x86-64 ELF64, static | 41 812 байт |
| Компилятор Windows | `bin/windows-x86_64/ruasm.exe` | x86-64 PE32+ console | 49 664 байта |
| Общая часть компилятора | `src/core/ruasm-core.asm` | исходный код RUASM | 128 939 байт |
| Полный исходник Linux | `src/generated/linux/ruasm.asm` | исходный код RUASM | 177 043 байта |
| Полный исходник Windows | `src/generated/windows/ruasm-windows.asm` | исходный код RUASM | 196 306 байт |

Исполняемые файлы Linux и Windows — программы для соответствующих хостовых ОС. Оба компилятора ориентированы на x86-64 и создают один и тот же формат результата `flat-binary`. Результат компиляции не является ELF executable, PE executable, COFF object, ELF relocatable object или слинкованной программой.

Linux-компилятор может собрать оба полных исходника: пересобрать Linux-компилятор и выполнить cross-build Windows PE. В опубликованном комплекте повторная компиляция Linux-исходника воспроизводит Linux-бинарник побайтно; компиляция Windows-исходника воспроизводит Windows PE побайтно. Исходник Windows близок к пределу размера входного файла: любые изменения нужно проверять через `--check`.

## 3. Модель работы

Вход: один файл исходного кода RUASM.  
Выход: один поток машинных байтов.  
Целевая ISA: x86-64 long mode.  
Максимальный размер результата: 65 536 байт.

Метки и определения `equ` не создают байтов. Директивы данных и инструкции создают байты в порядке размещения после разрешения символов и стабилизации layout. Компилятор не создаёт секции, таблицу символов объектного файла, релокации, таблицу импорта пользовательской программы или сценарий линковки. Он не вызывает системный компилятор или ассемблер для генерации результата.

Текущий компилятор состоит из двух хостовых оболочек и одной общей физической реализации парсера/IR/кодогенератора:

- Linux: ELF64 startup и ввод-вывод через системные вызовы Linux.
- Windows: PE32+ startup и ввод-вывод через Windows API.
- Общая часть: лексический разбор, синтаксический анализ, символы, layout, выбор инструкций и выдача байтов.

Linux-бинарник статически слинкован и не содержит таблицы секций ELF. Windows-бинарник — нативная консольная программа PE32+. Хостовые API не являются зависимостями создаваемых плоских бинарных образов.

## 4. Интерфейс командной строки

Имя исполняемого файла: `ruasm` в Linux и `ruasm.exe` в Windows.

```text
ruasm --help
ruasm --version
ruasm --version=json
ruasm --features
ruasm --features=json
ruasm input.asm --check
ruasm input.asm --check --diagnostics=json
ruasm input.asm -o output.bin
ruasm input.asm -o output.bin --quiet
ruasm input.asm -o output.bin --time
ruasm input.asm -o output.bin --diagnostics=json
```

| Назначение | Вызов | Поведение |
|---|---|---|
| Справка | `--help` | Выводит синтаксис команд и поддерживаемые режимы. |
| Версия | `--version` | Выводит название продукта и версию. |
| Контракт версии | `--version=json` | JSON схемы 1: идентичность, хост, цель, self-hosted и формат результата. |
| Возможности | `--features` | Человекочитаемая сводка. |
| Возможности JSON | `--features=json` | Полный манифест возможностей схемы 29. |
| Проверка | `input.asm --check` | Разбирает и проверяет файл без выдачи бинарного результата. |
| Проверка JSON | `input.asm --check --diagnostics=json` | Проверка со структурированной диагностикой в stderr. |
| Компиляция | `input.asm -o output.bin` | Создаёт плоский бинарный образ. |
| Тихий режим | `input.asm -o output.bin --quiet` | Скрывает обычное сообщение об успехе. |
| Замеры | `input.asm -o output.bin --time` | Выводит время, число layout passes, число коротких переходов и размер результата. |

Неизвестные аргументы, похожие на опции, считаются ошибкой использования. Не следует рассчитывать на недокументированные сочетания или порядок аргументов.

`--diagnostics=json` меняет только способ представления ошибок, но не семантику языка. Диагностика выводится в `stderr`. При успешной компиляции выходной файл содержит плоский поток байтов.

## 5. Машинно-читаемый интерфейс для агентов

### 5.1. Обнаружение версии

Запустите:

```sh
./bin/linux-x86_64/ruasm --version=json
```

Обязательные поля схемы 1:

- `schema_version`: целое число, сейчас `1`.
- `name`: `RUASM`.
- `version`: версия продукта, сейчас `1.11.5`.
- `host`: идентификатор хоста, например `linux-x86_64` или `windows-x86_64`.
- `target`: сейчас `x86_64`.
- `self_hosted`: логическое значение, сейчас `true`.
- `output_format`: сейчас `flat-binary`.

### 5.2. Обнаружение возможностей

Запустите:

```sh
./bin/linux-x86_64/ruasm --features=json > features.json
```

Ответ использует схему 29. Основные поля:

| Поле | Значение |
|---|---|
| `compiler` | Идентичность запущенного компилятора. |
| `output` | Формат результата и предел размера. |
| `source` | Пределы исходника, строки и токена; чувствительность к регистру; модель строк. |
| `directives`, `data` | Поддерживаемые директивы и семантика целочисленных данных. |
| `expressions` | Литералы и операторы выражений. |
| `registers`, `register_model` | Имена регистров, классы ширины, алиасы и поддержка ширин. |
| `instructions` | Мнемоники и описания поддерживаемых форм операндов. |
| `memory` | Ограничения адресации и диапазон смещения. |
| `symbols` | Ёмкость таблицы и детерминированная стратегия разрешения символов/layout. |
| `cli`, `statistics` | Контракт командной строки и поля `--time`. |
| `mnemonics` | Принимаемые написания инструкций, включая алиасы условий. |
| `intermediate_representation` | Публично описанный контракт statement/operand/AST. |
| `isa_model` | Модель декларативных ISA-дескрипторов и текущие записи. |

Манифест — точный контракт возможностей конкретной сборки. Некоторые формы представлены матрицами и декартовыми произведениями. Агент ОБЯЗАН разворачивать только измерения, явно указанные в соответствующем объекте. Например, `instructions.alu` задаёт только матрицу регистр-регистр и регистр-непосредственное значение. Из неё нельзя выводить поддержку memory-форм. Они отдельно указаны в `alu_memory` и `test_memory`.

Само присутствие мнемоники в `mnemonics` не означает реализацию всех её архитектурных форм. Авторитетны объект `instructions` и его поля форм операндов.

### 5.3. JSON Schema

Используйте следующие схемы:

- `spec/contracts/ruasm-version-v1.schema.json`
- `spec/contracts/ruasm-features-v29.schema.json`
- `spec/contracts/ruasm-diagnostic-v1.schema.json`

Примеры ответов — снимки Linux-бинарника из данного комплекта. Для другой платформы агент обязан запрашивать сам исполняемый файл; поле `host` будет отличаться.

## 7. Конвейер компиляции и внутренние контракты данных

Компилятор публикует часть внутренних деталей, поскольку они помогают агенту понимать обработку исходного файла. Это версионируемые детали реализации; агент не должен напрямую создавать эти структуры.

### 7.1. Statement IR v2

Каждая физическая строка может быть представлена упакованной 32-битной записью:

| Биты | Поле | Значение |
|---|---|---|
| 0..17 | `source_offset_u18` | Абсолютное смещение в исходном файле. |
| 18..25 | `kind_u8` | Класс statement. |
| 26..31 | `isa_index_u6` | Индекс ISA-реестра. |

Классы:

- `0`: пустая строка или комментарий.
- `1`: метка.
- `2`: объявление `equ`.
- `3`: директива данных.
- `4`: инструкция.
- `255`: неизвестная классификация, передаваемая каноническому парсеру для выдачи диагностики.

Индекс ISA — ссылка на общую таблицу; текст исходника остаётся публичным языковым интерфейсом. IR не является форматом пользовательского ввода.

### 7.2. Typed Operand IR v1

Текущая реализация использует два 8-байтовых слота операндов на statement. Публично описанные типы узлов:

- `1`: регистр r64.
- `2`: регистр r8.
- `3`: диапазон исходного текста memory-операнда с кэшированными полями адресации.
- `4`: диапазон исходного текста immediate-выражения со ссылкой на AST.
- `5`: регистр r32.
- `6`: регистр r16.

Узел памяти содержит индекс базового регистра, диапазон текста и упакованные флаги дополнительного индексного регистра/масштаба. Точные поля и биты перечислены в JSON. Не используйте резервные поля и недокументированные внутренние адреса.

### 7.3. Expression AST v1

AST использует узлы по 16 байт и поддерживает:

- беззнаковый 64-битный литерал;
- ссылку на символ;
- бинарную операцию;
- унарное отрицание.

Текущие коды бинарных операций: сложение, вычитание, левый сдвиг, логический правый сдвиг, побитовое AND и побитовое OR. Идентификаторы узлов начинаются с 1. AST — внутренняя структура; в исходнике следует писать выражения.

Корни AST кэшируются по позиции в исходнике, но значения вычисляются повторно в текущем окружении символов. Это необходимо для выражений, зависящих от адресов меток во время layout. Агент НЕ ДОЛЖЕН считать, что кэширование разобранного выражения делает его значение постоянным.

### 7.4. Разрешение символов

Зависимости `EQU` от других `EQU` разрешаются детерминированным графом и топологической сортировкой Кана. Правило разрешения равноприоритетных узлов — наименьший индекс в таблице символов. Адреса меток зависят от layout и пересчитываются при стабилизации. Циклы вызывают `E_EQU_CYCLE`, неразрешённые имена — `E_UNDEFINED_SYMBOL`.

### 7.5. Layout и оптимизация переходов

Компилятор повторно размещает исходник до стабилизации состояния символов и размеров. Поддерживаемые `JMP` и условные переходы могут кодироваться как signed rel8 (`-128..127`) или signed rel32. Компилятор автоматически сокращает переход, если это допустимо, и повторяет layout при необходимости. `CALL` всегда использует rel32. Перед финальной выдачей короткое смещение проверяется повторно; если оно не подходит, переход расширяется и layout запускается заново. Для циклов layout предусмотрен консервативный fallback. В патологическом файле он может оставить near-переход вместо минимального размера, но приоритетом являются корректность результата и сходимость.

`--time` показывает число проходов layout и число выбранных коротких переходов. Это телеметрия, а не обещание фиксированного количества проходов.

## 8. Диагностика и ошибки

Стабильные коды диагностики:

| Код | Значение |
|---|---|
| `E_SYNTAX` | Некорректный синтаксис или неподдерживаемая форма операндов. |
| `E_INPUT` | Ошибка пути или чтения входного файла. |
| `E_OUTPUT` | Ошибка создания, записи или фиксации выходного файла. |
| `E_RANGE` | Литерал, immediate, значение директивы данных, shift count или displacement вне диапазона. |
| `E_IDENTIFIER` | Некорректное или зарезервированное имя. |
| `E_DUPLICATE_SYMBOL` | Повторное объявление метки/EQU. |
| `E_UNDEFINED_SYMBOL` | Неразрешённый символ. |
| `E_SYMBOL_LIMIT` | Превышено 1 024 символа. |
| `E_OUTPUT_LIMIT` | Результат больше 65 536 байт. |
| `E_EQU_CYCLE` | Циклическая зависимость EQU. |

Объект диагностики схемы 1 обязательно содержит `code` и `message`; `line` и `column` опциональны. Нумерация строк и колонок начинается с 1. Если исходной позиции нет, допускается `line: 0` и `column: null`.

При ошибке компиляции/проверки нельзя использовать частично созданный результат. Путь публикации результата реализован и регрессионно проверяется так, чтобы не заменять существующий выходной файл при неудачной компиляции. Агенту РЕКОМЕНДУЕТСЯ сначала собирать во временный новый путь, проверять код возврата, затем проверять файл и только после этого переносить его в релизный каталог.

## 9. Детерминизм и воспроизводимая сборка

Для одинакового бинарника компилятора, одинаковых байтов исходника и одинаковых аргументов командной строки ожидается одинаковый результат. Выбор инструкций не зависит от случайного seed или времени суток. `--time` меняет только отчёт.

Пересборка текущего компилятора штатным Linux-бинарником:

```sh
mkdir -p build
./bin/linux-x86_64/ruasm src/generated/linux/ruasm.asm -o build/ruasm --quiet
cmp bin/linux-x86_64/ruasm build/ruasm
./bin/linux-x86_64/ruasm src/generated/windows/ruasm-windows.asm -o build/ruasm.exe --quiet
cmp bin/windows-x86_64/ruasm.exe build/ruasm.exe
```

В Windows нативный компилятор может пересобрать свой PE-образ:

```powershell
New-Item -ItemType Directory -Force .\build | Out-Null
.\bin\windows-x86_64\ruasm.exe .\src\generated\windows\ruasm-windows.asm -o .\build\ruasm.exe --quiet
if ($LASTEXITCODE -ne 0) { throw 'RUASM build failed' }
Get-FileHash .\build\ruasm.exe -Algorithm SHA256
```

Успех `cmp` означает побайтовое совпадение на машине, где выполнена команда. Для запуска и сборки исходников штатными RUASM-бинарниками не требуется FASM или другой ассемблер. Shell, PowerShell, `cmp` и утилиты хеширования в примерах используются только для оркестрации и проверки.

## 10. Протокол работы ИИ-агента

Для каждого генерируемого исходника агенту СЛЕДУЕТ:

1. Запросить `--version=json` и `--features=json` у точного бинарника, который будет запускаться.
2. Проверить `name`, `version`, `target`, `output.format` и `schema_version`.
3. Построить allow-list для конкретной мнемоники, порядка операндов, ширин регистров, memory-формы и типа immediate.
4. Генерировать lowercase-синтаксис, ASCII-идентификаторы, один statement на физическую строку и канонические операнды через запятую.
5. Не предполагать наличие неподдерживаемых языковых конструкций, ABI, секций, линковки или runtime.
6. Выполнить `input.asm --check --diagnostics=json`.
7. При ошибке прочитать структурированную диагностику и сделать минимальную локальную правку; не подбирать формы операндов наугад.
8. Компилировать в новый выходной путь.
9. Проверить код возврата, размер файла и ожидаемые байты/хеш, если они заданы задачей.
10. Только после этого публиковать или встраивать результат.

### Формат отчёта агента

При отчёте о компиляции агенту РЕКОМЕНДУЕТСЯ указать:

- версию RUASM и host;
- целевую архитектуру и формат результата;
- входной и выходной файл;
- результат проверки;
- результат компиляции и число выходных байт;
- результат проверки байтов/хеша, если он требовался;
- неподтверждённые предположения и внешние требования к ABI.

## 11. Границы текущей версии

RUASM 1.11.5 не является полной заменой FASM. Текущий компилятор не реализует полный x86-64 ISA, макросистему/препроцессор, включение файлов, строковые литералы, `org`, `align`, секции, генерацию relocatable ELF/COFF, релокации, линкер, объявления процедур/ABI, SDK ОС, отладчик или стандартную runtime-библиотеку. Точные ограничения по инструкциям находятся в машинном манифесте и спецификации языка.

Долгосрочные цели продукта: расширение охвата ISA, компактный машинный код, высокая скорость компиляции, явно заданная машинно-проверяемая семантика, снижение неоднозначности кода от агентов и применение в инструментальной среде суверенной ОС. Эта спецификация не утверждает, что RUASM уже превосходит FASM по общему функционалу или производительности.

Гипотеза agent-first-дизайна состоит в том, что узкий, явный и версионируемый контракт вместе с детерминированной диагностикой снизит число повторных попыток модели и ошибок генерации. Это проектная цель; эмпирическое утверждение об экономии токенов и надёжности агентов требует контролируемого набора задач и опубликованной методики.
